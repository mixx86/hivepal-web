    Connecting agents#

    There are two directions, and you can use both:

    1. Your agent reaches you. Claude Code, OpenClaw, n8n or a script messages your phone, waits for your reply, or calls you. A voice AI talks to you for the agent and hands it the transcript. Use the MCP server (or its HTTP version), the CLI or the relay's REST API.
    2. You reach your agents by phone. On a call (one the agent placed, or one you made with "Call agent" in the app), the voice AI can ask your agents for help. Each agent in agents.yaml is a tool for it, through consult_agent, and so are your MCP servers.

    MCP server (hivepal mcp)#

    hivepal mcp is an MCP server over stdio. Add it to any MCP client:

    claude mcp add hivepal -- hivepal mcp          # Claude Code

    { "mcpServers": { "hivepal": { "command": "hivepal", "args": ["mcp"] } } }

    The second form is the usual mcpServers config that most clients read. It uses the daemon's config (hivepal init), so run hivepal init and hivepal pair first. Other harnesses: see recipes.

    hivepal mcp --agent-name "Claude Code" sets the caller name the phone shows (useful when several agents share one relay), and --device dev_… (repeatable) rings only those phones instead of every paired one.

    call blocks until the call ends, and get_replies up to wait_s: raise the client's MCP tool timeout if it has a short one (Codex: 60 s, OpenClaw: 60 s, opencode: 30 s, Hermes: 300 s).

    Tool What it does
    send_message(text, reply_to?) Sends a message to the phone (a notification you can reply to inline). Returns msg_id.
    get_replies(wait_s?) Your new replies, each one returned once. wait_s waits up to that long for one (max 3600).
    call(reason, context?, urgent?) The phone rings. When you answer, the voice AI says why it's calling, talks with you, and hangs up when you're done. Returns the transcript, how long the call lasted, why it ended and which tools were used. Blocks until the call ends. Needs the [voice] extra and the voice provider's key (GEMINI_API_KEY by default; HIVEPAL_VOICE_PROVIDER picks another, see voice.md).
    status() Whether the relay is reachable and which phones are paired.

    context is everything the voice AI knows about the agent's work: put in it what to tell you, what to ask and what not to decide. If ~/.agentring/agents.yaml exists, the voice AI on these calls can also consult your agents, but only once you have spoken on the call: context may hold text the calling agent read elsewhere, and that alone must not start a tool (voice.md).

    With hivepal mcp --device, the call is private to those phones. If nobody answers, or an agent's answer comes after the call, nothing is sent as a message, because a message reaches every paired phone: the calling agent still gets the result.

    Before hivepal init, the server still starts and lists its tools; each tool call then answers with what is missing, so the agent can tell you.

    The server is a small JSON-RPC loop with no MCP SDK and no extra dependencies (see architecture). For an MCP URL instead of a local command, see Remote MCP (HTTP). HTTP-only clients such as n8n can also use the REST API (below).

    Remote MCP (HTTP)#

    hivepal mcp-http serves the same four tools over MCP Streamable HTTP at /mcp, for many users at once. Each user's agent sends its relay API key as a bearer token, so nothing about the user is configured on the server, and the agent's computer needs no daemon:

    claude mcp add --transport http hivepal https://mcp.example.com/mcp \
  --header "Authorization: Bearer ak_..."

    { "mcpServers": { "hivepal": { "type": "http", "url": "https://mcp.example.com/mcp",
                                 "headers": { "Authorization": "Bearer ak_..." } } } }

    Run it next to your relay (self-hosted: every key is checked against that one relay with GET /v1/status):

    hivepal mcp-http --relay-url https://relay.example.com          # listens on 127.0.0.1:8790
    Option Environment Default
    --host, --port HIVEPAL_MCP_HOST, HIVEPAL_MCP_PORT 127.0.0.1, 8790 Put TLS (Caddy, Traefik) in front of it.
    --relay-url HIVEPAL_RELAY_URL The relay. With a hub, its internal address (optional).
    HIVEPAL_HUB_ADMIN_URL, HIVEPAL_HUB_ADMIN_TOKEN_FILE or HIVEPAL_HUB_ADMIN_TOKEN Hub mode: keys are resolved to their tenant (cloud.md).
    --data-dir HIVEPAL_MCP_DATA_DIR ~/.agentring/mcp-http Per-user state, one SQLite file per tenant.
    --max-calls HIVEPAL_MCP_MAX_CALLS 4 Voice calls at once, all users together; one more gets the tool error busy.
    HIVEPAL_UPGRADE_URL none Hosted plans: where users raise their limits. Added to quota_exceeded tool errors and to the result of a call the relay cut off for minutes, so the agent can pass the link on. hivepal mcp (stdio) reads it too.
    --max-body HIVEPAL_MCP_MAX_BODY 1048576 Largest request body (bytes); larger gets 413.
    --allow-origin HIVEPAL_MCP_ALLOWED_ORIGINS (comma-separated) none Browser Origins allowed to use /mcp (* = any). Requests from any other Origin get 403; MCP clients that are not browsers send none.

    How it behaves:

    • Auth. No key, or one the relay (or hub) doesn't know: 401 with WWW-Authenticate: Bearer. A working key is remembered for 5 minutes (by its hash; keys are never logged).
    • Protocol. POST /mcp takes JSON-RPC (initialize, ping, tools/list, tools/call, notifications, notifications/cancelled; batches too). initialize returns an Mcp-Session-Id; send it back on later requests (an unknown or expired one gets 404: initialize again). Requests without a session id also work. DELETE /mcp ends the session and cancels its running requests; GET /mcp is 405 (the server sends nothing unprompted). GET /healthz is the health check.
    • Long calls. Quick requests get application/json. call, and get_replies with wait_s, get a text/event-stream (if the client accepts it) with a keep-alive comment every 15 s until the result, so proxies don't cut the request. Raise the proxy's read timeout anyway if it is shorter than a call. If the client hangs up, a waiting get_replies stops, with or without a stream; a phone call goes on until it ends.
    • Limits. Batches of up to 32 messages; up to 16 tool calls running at once per account (over it, 429 with Retry-After; HIVEPAL_MCP_MAX_INFLIGHT changes it). Connections and response sizes are capped too: see cloud.md.
    • Voice. call runs the voice AI on this server, with the provider and key from its environment (HIVEPAL_VOICE_PROVIDER, GEMINI_API_KEY, …) as for hivepal call --ai. agents.yaml is not used: the server never runs commands for its users.
    • State. Which replies get_replies already returned is kept per tenant (hub tenant id, or the relay id in self-hosted mode) in {data dir}/tenants/{id}.db, the same mirror the local daemon keeps, so every session of one user sees each reply once, also after a restart.

    With Docker, the daemon image (daemon/Dockerfile, entrypoint hivepal) runs it; for example as a service in deploy/docker-compose.yml, routed at /mcp by the proxy:

      mcp:
    build: ../daemon                 # or the hivepal-daemon image of a release that has mcp-http
    command: ["mcp-http", "--host", "0.0.0.0"]
    environment:
      HIVEPAL_RELAY_URL: http://relay:8080
      GEMINI_API_KEY: ${GEMINI_API_KEY}
    volumes: ["mcp-data:/config"]    # state in /config/mcp-http
    read_only: true

    agents.yaml#

    ~/.agentring/agents.yaml (or --agents PATH) lists what the voice AI may use during a call:

    agents:
  claude:
    description: Claude Code in my web app's repo. Code questions, CI status, deploys.
    command: [claude, -p, --permission-mode, plan, --, "{task}"]
    cwd: ~/code/webapp
    timeout_s: 600          # hard limit; the process is killed after it (default 600)
  ops:
    description: My ops scripts. Disk, backups, service status.
    command: [~/bin/ops-agent]   # no "{task}": the task arrives on stdin
    env: {OPS_PROFILE: prod}

mcp:                         # MCP servers over Streamable HTTP; their tools go straight to the voice AI
  - url: http://127.0.0.1:8787/mcp
    tools: [status, logs]    # allowlist; omit it to expose all of the server's tools
    headers: {Authorization: Bearer ...}
    • command is an argv list, never a shell string (a string is rejected). The task comes from a voice model, so it is only ever one argument: {task} is replaced inside the argument that contains it, and if no argument has it, the task goes to stdin. The agent's stdout is the answer. A non-zero exit is an error, with the end of stderr.
    • The task is never read as an option. As a whole argument with no -- before it, a task that starts with - is passed as Task: -…, so [claude, -p, "{task}"] is safe. You still choose what the agent sees: put -- before {task}, or text before it in the same argument ("Task: {task}"), and it is passed as it is.
    • The agent runs with your environment plus env and HIVEPAL_CALL_ID, in cwd. The call id lets an agent keep one session per call (see OpenClaw).
    • description matters: the voice AI picks the agent by it.
    • Over the phone, expose only what the caller should be able to do: use allowlists, and agents whose permissions you'd accept from someone holding your phone. The phone is paired to your relay, but the voice AI acts on what it hears.

    Check the file and try an agent without a call:

    hivepal agents                       # lists them; errors if the file is wrong
hivepal agents ask claude "Is CI green on main?"

    Then use it on calls:

    hivepal serve --ai                   # answers "Call agent" from the app
hivepal call "Deploy needs your OK" --ai

    How a consultation goes#

    consult_agent(agent, task) waits up to 20 s. If the agent answers in that time, the voice AI gets the answer right away. If not, it hears that the agent is working on it, tells you, and the call carries on. When the answer arrives, the voice AI gets it as a note and tells you. If the call has already ended, the answer is sent to your phone as a message. Each agent works on one task at a time; a second request for a busy agent is refused, so the model asks again later.

    From Python, Consultations(agents, answer_within_s=…, prompts=ConsultPrompts(…)) builds the tool (.tool()) for a VoiceAgent. Any tool of your own can do the same "answer later" trick: current_session() returns the call, and session.notify(text, respond=True) speaks up when you are done.

    Recipes by harness#

    hivepal doesn't care which harness you use: anything that speaks MCP can reach you, and anything you can run as a command can be consulted from a call.

    Your agent reaches you (MCP)#

    Harness Setup
    Claude Code hivepal connect claude-code, or by hand: claude mcp add hivepal -- hivepal mcp
    Codex hivepal connect codex, or by hand: codex mcp add hivepal -- hivepal mcp, then tool_timeout_sec = 1800 under [mcp_servers.hivepal] in ~/.codex/config.toml
    Cursor hivepal connect cursor (writes ~/.cursor/mcp.json)
    opencode opencode.json: "mcp": {"hivepal": {"type": "local", "command": ["hivepal", "mcp"], "timeout": 1800000}}
    OpenClaw hivepal connect openclaw, or by hand: openclaw mcp set hivepal '{"command":"hivepal","args":["mcp"],"requestTimeoutMs":1800000}'
    Hermes hivepal connect hermes, or by hand in ~/.hermes/config.yaml: mcp_servers: {hivepal: {command: hivepal, args: [mcp], timeout: 1800}}
    Grok Build grok mcp add hivepal -- hivepal mcp (its default tool timeout is long enough). With hivepal cloud, the plugin instead: grok plugin install mixx86/hivepal#plugins/hivepal --trust and HIVEPAL_API_KEY in your environment (plugins/hivepal)
    Anything else the mcpServers JSON above, the hivepal CLI, or the REST API

    Add skills/hivepal where the harness reads skills, so the agent knows when to message and when to call (hivepal connect does it for you).

    hivepal connect (Claude Code, Codex, Cursor, OpenClaw, Hermes)#

    One command sets up the whole thing, and is safe to run again:

    hivepal connect claude-code                  # or: codex, cursor, openclaw, hermes
hivepal connect hermes --dry-run             # show what would change
HIVEPAL_API_KEY=ak_... hivepal connect hermes --url https://agentring.io/mcp   # hosted MCP server
    1. MCP server. Registers hivepal mcp (by absolute path, with --agent-name OpenClaw/Hermes so the phone shows who is calling) through openclaw mcp set, or in $HERMES_HOME/config.yaml (default ~/.hermes; the old file is kept as config.yaml.bak-hivepal). The tool timeout goes to 30 minutes, since a call lasts as long as the conversation. With --url, the remote server instead: the key goes to the harness's .env (~/.openclaw/.env, ~/.hermes/.env, mode 0600) and the config only says Bearer ${HIVEPAL_API_KEY}. Claude Code: claude mcp add-json hivepal … --scope user (every project). Codex: the [mcp_servers.hivepal] table in ~/.codex/config.toml (the rest of the file is kept). Cursor: ~/.cursor/mcp.json. --url is for OpenClaw and Hermes only.
    2. Skill. Installs skills/hivepal (OpenClaw: openclaw skills install --global; Hermes: ~/.hermes/skills/hivepal; Claude Code: ~/.claude/skills/hivepal). Codex and Cursor read the MCP server's own instructions. --no-skill skips it.
    3. Consult from a call. Adds the harness to ~/.agentring/agents.yaml (Claude Code: claude -p, Codex: codex exec; not Cursor) with the recipe below (comments in the file are kept). Not with --url: a remote server never runs commands. --no-consult skips it.

    Then OpenClaw picks the server up on the next turn (openclaw mcp probe hivepal checks it); in Hermes run /reload-mcp or start a new session (hermes mcp test hivepal). The skill also carries a setup guide (references/setup.md): install it first (openclaw skills install @mixx86/hivepal, hermes skills install mixx86/hivepal/skills/hivepal) and ask your agent to "set up hivepal".

    You consult your agent from a call (agents.yaml)#

    agents:
  claude:
    description: Claude Code in my web app's repo. Code questions, CI status.
    command: [claude, -p, --permission-mode, plan, --, "{task}"]
    cwd: ~/code/webapp
  codex:
    description: Codex in my web app's repo. Code questions, CI status.
    command: [codex, exec, --sandbox, read-only, --ephemeral, --, "{task}"]
    cwd: ~/code/webapp
  opencode:
    description: opencode in my web app's repo.
    command: [opencode, run, "Task: {task}"]
    cwd: ~/code/webapp
  hermes:
    description: My Hermes agent. Email, calendar, research.
    command: [hermes, -z, "Task: {task}"]
  openclaw:
    description: My OpenClaw assistant. Messages, calendar, home.
    command: [sh, -c, 'exec openclaw agent --agent main --session-id "hivepal-${HIVEPAL_CALL_ID:-test}" --message="$1"', sh, "{task}"]

    Keep only the ones you use, and check each with hivepal agents ask <name> "…". They start read-only or with the harness's own approval rules. Widen them on purpose, knowing the voice AI acts on what it hears:

    • Claude Code: plan can look but not change anything. To let it act, use --permission-mode acceptEdits with a narrow --allowedTools list.
    • Codex: --sandbox workspace-write lets it edit files under cwd. Add --skip-git-repo-check if cwd is not a git repo.
    • opencode: uses its permission config; don't add --auto (approves everything). With opencode serve running, --attach http://localhost:4096 skips the start-up cost.
    • Hermes: -z prints only the final answer. Don't add --yolo for the phone.

    OpenClaw#

    openclaw agent runs one turn through your running gateway. The sh -c script is fixed text: the task arrives as $1 and is never parsed by the shell. The call id gives each call its own OpenClaw session, so a second question on the same call keeps the context of the first.

    Agents behind an HTTP API#

    For an agent that only runs as a server (an OpenAI-compatible endpoint such as the OpenClaw gateway's or Hermes' API server, a webhook, your own service), point command at a small script that reads the task on stdin and prints the answer:

    #!/bin/bash
# ~/bin/ask-agent: task on stdin, answer on stdout. Set AGENT_URL, AGENT_MODEL, AGENT_KEY.
set -euo pipefail
jq -Rs --arg m "$AGENT_MODEL" --arg u "hivepal-${HIVEPAL_CALL_ID:-test}" \
  '{model: $m, user: $u, messages: [{role: "user", content: .}]}' \
| curl -sf "$AGENT_URL/v1/chat/completions" -H "Authorization: Bearer $AGENT_KEY" \
    -H 'content-type: application/json' -d @- \
| jq -er '.choices[0].message.content'

      myagent:
    description: ...
    command: [~/bin/ask-agent]          # no "{task}": it goes to stdin
    env: {AGENT_URL: "http://127.0.0.1:8642", AGENT_MODEL: "...", AGENT_KEY: "..."}   # what your server expects

    REST API (n8n, scripts)#

    Every action is one HTTPS request to your relay with the daemon's ak_… API key (hivepal status --json prints the relay URL; the key is in ~/.agentring/.env). See protocol/relay.openapi.yaml:

    curl -s https://relay.example.com/v1/messages -H "Authorization: Bearer $HIVEPAL_API_KEY" \
  -H 'content-type: application/json' -d '{"text": "Backup finished"}'

    Replies come from GET /v1/messages?after=<msg_id>, or live over the WebSocket. A call over plain REST only rings the phone: the voice needs a worker in the room, which is the daemon (hivepal call --ai, or the call MCP tool). See examples/ for an n8n workflow.
