    Architecture (F1)#

    Status: M1 done and tested on a real phone. M2 (calls) implemented and tested on a Pixel 6 / Android 16; LiveKit in the deploy compose still to do. Voice AI lands in M3.

    hivepal lets any AI agent (Claude Code, OpenClaw, n8n, plain scripts…) place a VoIP call to the user's phone, send it messages, and receive calls from it. The phone rings like a real call, even locked and in Doze. No PSTN, no phone numbers, no Twilio.

    F1 scope: one user, one agent, Android only, self-hosted, no accounts.

    Component Responsibility Stack
    relay Pairing, device registry, call state machine + ring timeout, message store, event log + fan-out (WS), push (FCM), LiveKit room/token minting, LiveKit webhook. Source of truth for calls and messages. Node 22, TypeScript, Fastify 5, @fastify/websocket, node:sqlite (no native deps), livekit-server-sdk, jose; FCM HTTP v1 over plain fetch (no firebase-admin)
    daemon Agent-side endpoint. CLI, MCP server, local HTTP API, persistent relay connection, voice worker. Mirrors calls/messages into its own SQLite and stores transcripts + summaries. Python ≥ 3.11, uv, typer, httpx, websockets, Starlette/uvicorn, official mcp SDK, livekit realtime SDK (optional extra hivepal[voice])
    app-android Pairing (QR), push handling, self-managed ConnectionService, CallStyle + full-screen intent, LiveKit audio, messages thread. Kotlin, Compose, Material 3, OkHttp, kotlinx.serialization, Room, CameraX + ML Kit barcode, LiveKit Android SDK, Firebase Messaging
    livekit-server SFU; handles NAT traversal (ICE/TURN). One room per call. upstream image, self-hosted
    caddy Automatic TLS, reverse proxy. upstream image

    Why a /protocol folder (small addition to the brief)#

    Three languages consume the same contract. protocol/relay.openapi.yaml is the only place where the REST API and the event payloads are defined:

    • relay (TS): openapi-typescript → relay/src/generated/.
    • daemon (Python): datamodel-code-generator → pydantic v2 models.
    • app (Kotlin): hand-written @Serializable classes (generators for kotlinx are weak), kept honest by a unit test that round-trips every file in protocol/examples/.

    CI fails if generated code is stale or a fixture doesn't round-trip.

    Key design decisions (please review)#

    1. Commands over REST, events over WS (+FCM). Every state change is a REST call (works when the app was just woken by FCM and has no socket yet; easy to retry, easy to describe in OpenAPI). The WebSocket is a read-only stream of events, resumable by seq. FCM carries the subset of events that must wake the phone.
    2. One event log with a global seq. The relay persists every event; clients reconnect with after_seq and get what they missed. No lost replies when the daemon is offline.
    3. LiveKit tokens are not sent inside call.invite (deviation, needs your OK). The callee gets its token in the response of POST /v1/calls/{id}/accept. Reasons: tokens never transit Google's FCM; the token is minted only when needed so a short TTL (120 s) can't expire while the phone rings or while a delayed push is in flight; and the accept call is the atomic "first device wins" point. Cost: one extra HTTPS round trip (~50–150 ms) between tapping "answer" and joining the room. The caller still gets its token immediately in the POST /v1/calls response, so the voice worker is already in the room when the phone joins.
    4. Pushes are signed. At pairing the device receives a per-device push_secret; every FCM payload carries HMAC-SHA256(push_secret, event) plus relay_id. The app drops anything that doesn't verify. This is how "the app only accepts calls from the paired relay" is enforced, even if a Firebase project is ever shared.
    5. Extra call states (small deviation): besides ringing → active → ended and ringing → missed | declined, add ringing → canceled (caller hung up before answer). Also an informational call.ringing event (the phone actually displayed the call) — useful to measure the M2 "< 5 s" target and to tell "not delivered" from "ignored".
    6. One call at a time (F1): POST /v1/calls returns 409 busy while another call is ringing or active.
    7. Multiple devices allowed, ring all; group calls (changed in M2 at the user's request: was "first accept wins"). Every paired phone rings and any of them may answer while it rings; they share the room (the user and their brother on the same call with the agent). A phone declining or hanging up only affects itself. While the call is active, any paired phone not on it may join later ("join the call", POST /v1/calls/{id}/join), e.g. after its ring ended, after declining or after hanging up.
    8. Daemon ↔ relay auth with a single API key (HIVEPAL_API_KEY) generated by the relay on first start (or set via env). Device auth with a long-lived HS256 device_jwt checked against the device table on every request, so revocation is immediate.
    9. consult_agent command backend uses an argv list, not a shell string (M3): command: ["claude", "-p", "--", "{task}"]. The task comes from a voice model and must never be interpolated into a shell, or read as an option.
    10. Single hostname (M2): Caddy routes /v1/* to the relay and /rtc* to LiveKit, so the quickstart needs one DNS record. LiveKit's admin API (/twirp*) and the relay's LiveKit webhook are internal only (404 from outside); the relay reaches LiveKit over the compose network. LiveKit media goes over UDP 50000–50100 (+ TCP 7881 fallback).
    11. Firebase configured at runtime. The relay reads the user's google-services.json and returns its public client values as push_config in the pair response; the app initialises Firebase with them. One prebuilt APK therefore works with anyone's own Firebase project (no rebuild), which keeps the quickstart short.
    12. Jetpack Core-Telecom instead of a hand-written ConnectionService (M2 deviation, accepted). Incoming calls are registered with androidx.core:core-telecom (CallsManager.addCall), which uses the platform CallControl API on Android 14+ and a ConnectionService below it. Telecom is optional: if addCall fails or times out (3 s) the call still rings through our own foreground service (phoneCall type) + CallStyle notification + full-screen intent, with LiveKit's AudioSwitch doing the routing. With Telecom, the system owns audio routing (LiveKit uses NoAudioHandler). Settings has a switch to turn Telecom off on misbehaving devices. Research behind this: docs/voip-research.md.
    13. Placeholder package id dev.agentring.app for Android. Change it if you own a domain.

    Accepted deviations#

    • M3 voice without livekit-agents (merged in #2, at the user's request): the voice worker uses the plain livekit SDK (already used by the M2 echo worker) and talks to the model's realtime WebSocket API directly through a small RealtimeBackend interface. Fewer dependencies (supply-chain policy) and full control of turn-taking, group-call mixing and tools. Details in voice.md.
    • More voice providers (M3, at the user's request, issue #12): besides Gemini Live and OpenAI Realtime, Grok Voice (xAI, same protocol as OpenAI) and Phonic, each one RealtimeBackend class. One setting picks it for the CLI and the MCP server alike (--provider / HIVEPAL_VOICE_PROVIDER); Gemini stays the default for its free tier.
    • MCP server without the mcp SDK, stdio only (M5, at the user's request): hivepal mcp is a small JSON-RPC loop over stdin/stdout (mcp_server.py) with the tools send_message, get_replies, call and status; no new dependencies, as for the voice side. Details in agents.md.
    • Remote MCP server over Streamable HTTP (for hivepal cloud, cloud.md): hivepal mcp-http (mcp_http.py) serves the same tools to many users at once, each with their relay API key as bearer token; also without an SDK or web framework (a small HTTP/1.1 server on asyncio streams). Both transports share one tools implementation in mcp_server.py.

    • agents.yaml (M3): the voice AI's tools come from one file — command agents (consulted with consult_agent, argv lists only) and MCP servers with allowlists. A slow agent's answer reaches the call as a note, or the phone as a message once the call is over.

    • hivepal cloud: hub mode (at the user's request, 2026-11-01): the relay can host many isolated tenants (HIVEPAL_HUB=1), each a full relay instance with its own SQLite file under /t/{tenant_id}, plus an admin API for a control plane and per-tenant limits (402 quota_exceeded, end_reason: quota). This lifts F1's "one user, no accounts" for the hosted version only; self-hosted is unchanged. The control plane (accounts, billing) lives in a private repo. Details in cloud.md.

    • The relay delivers to agents and keeps their memory (Hivepal fork, at the user's request, 2026-11-20, issue #41): besides REST, an agent can hear from the user through a wake-up email and/or a Markdown mailbox the relay writes in git, in a repository per agent kept in the relay (served read-only over git's dumb HTTP protocol at /v1/agents/{id}/mailbox.git) and/or an external repository it pushes to with its own SSH deploy key. Bots can also keep a memory of their Hivepal conversations: Markdown (each day's conversation in the mailbox's history/) and/or SQLite (search at /v1/agents/{id}/memory, or download it as a file). The mail account, the repository and these choices are runtime settings stored in the relay (/v1/settings/*), changed by the relay key or the user's phones; the relay runs git as a child process with argv lists and only https/ssh transports. Details in multiagent.md.

    • UnifiedPush next to FCM (Hivepal fork, at the user's request, 2026-11-19, issue #12): a phone may wake through a UnifiedPush distributor (ntfy, NextPush…) instead of FCM, so neither the phone nor the relay needs Google. The phone gives the relay its endpoint (POST /v1/device/unifiedpush); the relay POSTs the same signed PushData map there, as JSON, with RFC 8030 TTL and Urgency headers, encrypted for the app (RFC 8291 aes128gcm, with the connector's Web Push keys) so the distributor's server only sees ciphertext; it falls back to FCM when the phone clears it. Endpoints must be https:// on a public host (checked again after DNS) and redirects are not followed, so a paired phone can't make the relay reach its internal network. FCM remains the default when the relay configures it; without FCM, onboarding selects UnifiedPush automatically when a distributor exists and otherwise guides the user through installing ntfy. Settings → Notifications still lets a user choose either channel.
